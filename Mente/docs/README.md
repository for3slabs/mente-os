---

## What this folder is

Everything that **explains** rather than governs. A rule in `rules/` states the conclusion; the
analysis that produced it lives here. A validator in `bin/` measures; the numbers it measures land
here. Four kinds of content share this folder:

| Kind | What it is | Written by |
|---|---|---|
| 🤖 **generated** | indexes, metrics, states — rebuilt from the tree | a script, never a person |
| 🏗️ **architecture** | how the engine itself works, with diagrams | whoever maintains the engine |
| 🔬 **analysis** | an investigation, dated, that led to a decision | whoever investigated |
| 📋 **plans** | how a large piece of work will be carried out | whoever plans it |

---

## ⛔ THE MOST IMPORTANT RULE IN THIS FOLDER

> ## 🤖 A generated file is NEVER edited by hand.

Files rebuilt by a script carry this header, and it is not decoration:

```
<!-- 🤖 GENERATED by bin/<script> — DO NOT EDIT BY HAND.
     Hand edits are lost on the next run. Regenerate: bin/<script> -->
```

**Two things go wrong when someone edits one anyway.** The edit disappears on the next run —
annoying but visible. Worse: between the edit and the next run, the file states something the
tree does not, **while still being read as measured truth**.

⭐ **A hand-maintained index goes stale silently and keeps being believed.** That is the failure
this whole mechanism exists to prevent: an index that claimed a document count that had not been
true for a long time, and nothing noticed, because an index looks authoritative by nature.

---

## ⭐ WHY THE GENERATED FILES EXIST AT ALL — the metric, never the number

The rule across the whole system: **a live number is never written into prose.**

```
⛔  "the battery runs N checks"        ← frozen the moment it was typed
✅  "the battery is green — the count is in docs/METRICS.md"
```

**A number copied by hand is correct exactly once.** Every document that repeats it becomes wrong
the moment the value moves, and nothing announces it — the document keeps reading as confident as
the day it was written.

So documents name the **metric**; this folder holds the **value**:

| Generated file | Holds | Rebuilt by |
|---|---|---|
| the metrics file | ⭐ every live number in the system | the metrics generator |
| the index | every document that exists | the index generator |
| the states file | which blocks exist and their health | the index generator |
| the decisions file | every ADR, collected | the index generator |

⚠️ **The pending-criterion file is a hybrid worth understanding:** its *count* is stamped by the
generator, while its *body* is written by hand — because it describes **what** is missing, not
**how many**. That is the correct split: the machine owns what it can measure, the person owns
what only judgment can state.

## What travels, and what does not

⚠️ This is the folder where the engine/instance line runs **through the middle**, not around it.

| ✅ Travels with the engine | ⛔ Never travels |
|---|---|
| `architecture/` — how the engine works | 🤖 every generated file — regenerated on each machine |
| this README | the workspace file — it describes ONE machine |
| generic method documents | the pending-criterion file — it names an owner |
| | `analysis/` and `plans/` about a specific project |

⭐ **Why the generated files do not travel even though they are useful:** a committed index would
arrive listing documents that do not exist on the new machine, and metrics would arrive stating
numbers measured somewhere else. **A clone would start with a report about a system that is not
its own** — and it would look authoritative. One command rebuilds them correctly in seconds.

⛔ **The workspace file never travels either.** It describes which repo is which on one specific
computer. A clone inheriting it gets a map of somebody else's machine — and the checks that read
it turn red pointing at paths that do not exist.

## What goes in here, and what does not

| ✅ Belongs here | ⛔ Does not |
|---|---|
| an analysis that led to a decision | the decision itself — that is an ADR in `rules/decisions/` |
| a plan for a large piece of work | the work — that is a block in `work/blocks/` |
| how the engine works, explained | how it must be used — that is a rule |
| a generated report | anything a person maintains by hand that a script could measure |

⚠️ **The line against `rules/`:** a rule is short and binding; a document here is long and
explanatory. When a rule starts carrying its full reasoning, move the reasoning here and leave the
rule pointing at it. **A law nobody finishes reading is a law nobody applies.**

⚠️ **The line against `work/blocks/`:** a plan describes what *will* be done; a block *is* the
doing, with its contract and its state. A plan that starts tracking progress has become a block
in the wrong folder.

## The subfolders

| Folder | Holds | Travels? |
|---|---|---|
| `architecture/` | how the engine runs — diagrams, anatomy, structure | ✅ engine |
| `analysis/` | dated investigations | ⛔ project-specific |
| `plans/` | how large work will be carried out | ⛔ project-specific |

⭐ **Date an analysis in its filename or header, always.** An investigation is true *as of a
moment*: the tree it measured has moved since. An undated analysis gets read as current forever,
and it is the most convincing kind of wrong document — it was accurate when written.

---

## ⚠️ Before you add a document here — the four questions

1. **Is it generated or written?** If a script could measure it, a script must — a hand-written
   number is a future lie.
2. **Does it belong to the engine or to a project?** Engine documents travel; project ones do not.
   Getting this wrong is how a clone inherits somebody else's history.
3. **Is it dated?** Analyses and plans need a date. Contracts and architecture do not — they
   describe what *is*.
4. **Is it the conclusion or the reasoning?** Conclusions go to `rules/` or an ADR. Reasoning
   stays here, and the conclusion points back at it.
